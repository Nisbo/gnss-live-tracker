# US915 · experimental support (0.27.0)

The same GNSS Live Tracker firmware now supports EU868 and US915. EU868 remains
its initial setting, and upgrades migrate existing EU868 settings without changing
WLAN profiles, tracks, satellite history or OTAA credentials. From 0.30.4, older
saved sessions require one fresh join to renegotiate receive-window parameters. As of 0.28.0, additional high-band regions are available experimentally; see
[the region guide](REGIONS.md).

**US915 has software test coverage only. No US915 join, uplink or downlink has
been tested with a physical US915 gateway.** A successful build is not a radio test. This is
an experimental feature, not a statement of regional certification or full
LoRaWAN conformance.

## Set up a US915 device

1. Register the device in the matching LoRaWAN network. With the present stack,
   select LoRaWAN 1.0.2 and Regional Parameters 1.0.2 revision B.
2. Choose the US915 frequency plan in the network and gateway configuration.
3. In the tracker, open **LoRaWAN → Region**, select **US915**, then the channel
   group matching that gateway. The selector initially suggests **FSB2 for TTN**:
   uplink channels 8–15 (903.9–905.3 MHz) plus channel 65 (904.6 MHz / 500 kHz).
   Other FSB1–8 groups and the full 64+8-channel plan are available. The full plan
   is intended for matching multi-channel gateway deployments.
4. Choose a starting data rate and ADR as required. SF7/125 kHz is DR3 in US915,
   not DR5 as in EU868. US915 also offers SF8/500 kHz (DR4); SF11 and SF12 are not
   US915 uplink options. Downlinks can use SF12–SF7 with 500 kHz bandwidth.
5. Enter the device's own DevEUI, JoinEUI and AppKey. Install the **single current
   TTN decoder** downloaded from the tracker, for all packet profiles.
6. Save and confirm the network change. A change of region or channel group
   causes a restart and fresh OTAA join. The old session is not reused for a
   different network plan. WLAN and recordings are retained. DevNonce state is
   retained, too.

US915 uses its regional join data-rate alternation and RX1 channel mapping;
RX2 starts at 923.3 MHz / DR8. The selected FSB is also used for join attempts and
channel recovery. A network can subsequently supply its own session parameters
and channel mask. The stored channel-group choice identifies the plan used for
session restoration; it does not override every accepted network MAC command.

The firmware continues to cap its requested V2 output at **14 dBm** before FEM
gain compensation. It does not increase output to the US915 stack's higher
regional default. ADR power commands can therefore have the same capped output
for several indices. Output is a configured target, not a measured RF value.

## Packet sizes at DR0

Basis, Standard and Systemdetails normally use 23, 24 and 38 bytes. US915 DR0
(SF10 / 125 kHz) allows only 11 application bytes before pending MAC options:

| Format | Length | Included measurements |
| --- | --- | --- |
| Normal selected profile | 23 / 24 / 38 bytes | Existing profile contents |
| Compact, format 6 | 11 bytes | Fix/recent/overflow flags, full 32-bit latitude and longitude, total used/reported satellite counts |
| Compact, format 7 | 9 bytes | Same flags and coordinates, without satellite totals |

Coordinates retain 1e-7 degree encoding precision. This is encoding precision,
not a claim about GNSS accuracy. Compact packets omit GNSS measurement time,
sequence, altitude, speed, HDOP and system details. The decoder omits unavailable
fields; a reception timestamp from TTN is not a GNSS measurement timestamp.

The 9-byte form also leaves room for a two-byte MAC reply. If fewer than nine
application bytes fit, pending MAC control data is sent separately before the
next position. Control-only attempts are bounded by the position interval;
they do not count as a position report. The US915 MAC answer queue is bounded
to 11 bytes, including sticky replies, so it remains sendable after an ADR drop
to DR0. A full queue rejects additional answers; the network must repeat those
requests. This limit and interoperability with real network traffic still need
US915 field validation.

Packet sizing queries do not change radio data rate, power, channel masks or
ADR counters. The query accounts for the next ADR step and pending MAC bytes.
The browser shows both the configured profile and the projected smaller packet.
At higher US915 data rates, all three normal profiles fit. The firmware does not
force a faster rate merely to fit a larger packet.

## Validation and remaining field tests

The automated host tests use the production US915/RegionCommon code with a
recording radio stub: all 72 channel frequencies, all channel-group masks,
join alternation, TX parameters, RX1 mapping across 72 channels and six downlink
rates, RX2 defaults, payload limits and ADR fallback. Additional tests compile
the production MAC size-query/validation functions and HTTP configuration code,
exercise NVS migration/rejoin handling, backup validation, browser estimates and
round-trip the C-generated 9/11-byte payloads through the shared decoder.

These tests do not validate RF behavior, receive timing, gateway compatibility,
network ADR convergence or a complete US915 session. Those require a tracker
and suitable gateway in a US915 deployment. Useful field-test feedback includes the selected frequency plan, FSB, join
results, uplinks, downlinks, ADR behavior and decoded compact packets.

Run the relevant local tests from the workspace root:

```sh
python3 tests/run_us915.py
```
